# LiYaxuan C4A 方案设计文档

> 挑战：C4A 技能提交自动评审（Automated Skill Submission Evaluator）
> 提交者：LiYaxuan（李亚轩）
> 完成级别：Level 1 文件采集器 ✅ + Level 2 完整性检查器 ✅ + Level 3 质量评审器 ✅ + Level 4 完整评审系统 ✅

---

## 一、要解决的问题

C4（技能分享与传播）要求每位同学提交一个技能包，但群里文件混杂，老师无法快速回答：

- 谁交了？谁没交？（采集与分组）
- 交的五个必备文件齐不齐？（skill说明 / 可执行内容 / demo / 教学说明 / AI日志）
- 技能本身合不合格？（C4 四条件：可复用 / 可执行 / 可验证 / IO 明确）
- 能不能自动给出初步评审，而不是等人肉阅卷？

现有 `wechat-doc-mapper` 只能做"收发室"（扫描→分类→缺口分析），C4A 把它升级为"自动阅卷系统"（完整性检查 + 质量评分 + 改进建议）。

## 二、系统架构

```
WeChat 群文件夹（本地路径）
        ↓
┌─────────────────────────────────────────────┐
│ Stage 1 文件采集与作者识别                    │
│   · 递归扫描 + `_C4_` 标记识别               │
│   · 作者提取链：文件名 → 文件夹 → 元数据 → 头部 │
│   · 非规范命名回退 + Unknown 标记             │
├─────────────────────────────────────────────┤
│ Stage 2 提交完整性检查（5 项必备交付物）        │
│   · 文件名信号 + 内容信号 + 扩展名偏好三通道检测 │
│   · 输出 ✅ 齐全 / ⚠️ 部分缺失 / ❌ 严重缺失    │
├─────────────────────────────────────────────┤
│ Stage 3 质量评审（C4 四条件）                  │
│   · 规则引擎：check item 谓词化 + 信号打分     │
│   · LLM 深审（可选）：国产大模型 API 深度点评   │
│   · 每条件输出 评级 + 依据 + 改进建议          │
├─────────────────────────────────────────────┤
│ Stage 4 报告生成                              │
│   · Markdown 报告（班级总览/作者详情/排名/建议）│
│   · Excel 详表（4 Sheet）                     │
│   · JSON（机器可读，供上层 Agent 集成）        │
│   · 版本追踪（_v2/_v3 迭代轨迹）              │
└─────────────────────────────────────────────┘
```

## 三、评审维度定义

### 3.1 完整性检查（5 项必备交付物）

| 必备文件 | 检测信号（文件名 / 内容 / 扩展名） |
|----------|----------------------------------|
| Skill 说明文档 | `skill说明`/`skill_doc`/`skill-doc`；内容含"使用场景/输入/输出/解决什么问题"；.md/.pdf/.docx |
| 可执行内容 | `.skill`/`.py` 等可执行扩展名优先；文件名含"技能/skill"；内容含代码块/def/class/import/YAML frontmatter |
| Demo | `demo`/`演示`/`截图`/`录屏`；.mp4/.mov/.png/.jpg/.gif |
| 教学说明 | `教学说明`/`tutorial`/`teaching`/`上手指南`；内容含"上手/步骤/常见坑/安装" |
| AI 日志 | `AI日志`/`AI_log`/`ai-log`；内容含"使用的 AI/prompt/迭代次数/ChatGPT/Claude" |

### 3.2 质量评审（C4 四条件，每项 0~1 分）

| 条件 | 权重 | 检测的 check items |
|------|------|--------------------|
| 可复用 Reusable | 25% | 有安装说明；无硬编码绝对路径/凭据（负向信号）；列出环境要求；平台无关或注明平台 |
| 可执行 Executable | 25% | 含可运行代码/prompt/workflow；.skill 结构有效；无明显语法错误；有 YAML frontmatter |
| 可验证 Verifiable | 25% | 有测试用例/示例；定义预期输出；demo 展示真实结果；成败标准清晰 |
| IO 明确 Clear I/O | 25% | 有"输入X，输出Y"一句话；输入类型/格式明确；输出类型/格式明确；边界输入有说明 |

评级规则：满足 ≥2 项 check item → ✅；满足 1 项 → ⚠️；0 项 → ❌。
综合分 = 完整性分 × 0.4 + 质量分 × 0.6（完整性分 = 已交文件数 / 5）。

## 四、技术选型：规则 + LLM 混合（关键设计决策）

| 方案 | 优点 | 缺点 | 我的取舍 |
|------|------|------|----------|
| 纯规则（关键词/正则） | 确定性强、速度快、零成本、离线可跑 | 覆盖率低、易误判 | **主引擎**：完整性检查必须确定可靠，误判代价高（老师信不过） |
| 纯 LLM | 理解力强、灵活 | 不确定、慢、贵、不可复现 | 不作为评分主依据，避免"今天评 3 分明天评 4 分" |
| **规则 + LLM 混合** | 规则快筛 + LLM 深审 | 架构复杂 | **最终方案** |

**为什么选混合：**
1. **完整性检查（交没交齐）是客观事实**，必须零误判 → 纯规则，信号可审计；
2. **质量评审是主观判断**，规则先按 check item 给出可复现评分，再让国产大模型（Qwen/DashScope，可选）做深度点评，发现规则层漏检问题并生成个性化建议；
3. **降级友好**：未配置 LLM API 时，规则引擎完整运行，评审能力不依赖云端。

## 五、拿来主义：从 wechat-doc-mapper 改造

| 拿了什么 | 改了什么 | 为什么 |
|----------|----------|--------|
| `inventory_folder` 递归扫描逻辑 | 增加 `_C4_` 标记聚焦识别与版本号（_v2/_v3）提取 | C4A 只关心 C4 提交，且要追踪迭代 |
| 作者识别回退链（文件名→文件夹→元数据→文档头） | 正则改为 C4 命名规范专用（`姓名_C4[_X]_内容.扩展名`） | C4 命名规范是评审正确性的前提 |
| YAML 驱动的信号评分思想（challenges.yaml） | 换成 `c4_rubric.yaml` 评审规则库（5 项交付物 + 4 条件） | 评审标准可配置、可审计、可复用 |
| Excel 输出框架（openpyxl 4 Sheet） | 改为评审数据（作者×条件矩阵、缺失项、班级统计） | 从"文档清单"变为"成绩单" |
| **新增（wechat-doc-mapper 没有的）** | 完整性检查器、四条件质量评审器（check item 谓词化）、LLM 深审适配器、版本追踪、Markdown 评审报告模板 | 这是"收发室 → 阅卷系统"的核心跃迁 |

## 六、文件获取方案（开放题）

本机环境无法直接访问微信群文件，采用**「本地文件夹路径」通用接口**设计（与挑战要求一致）：
- 用户把微信群文件手动/同步下载到任意文件夹 → 技能接受该路径即可工作；
- 测试语料：2 份课程材料中的真实技能（wechat-doc-mapper、skill-explainer，原件打包为 .skill）+ 3 份按真实形态构造的模拟同学提交（完整/部分/低质量三档），数据来源在评审报告中透明标注。

## 七、测试与验证

- **测试语料**：5 位作者、21 个文件，含完整/部分/严重缺失三档、命名不规范、非 C4 混入等边界；
- **预期结果**：3 人完整提交、1 人部分提交、1 人严重缺失；质量评分区分度明显（1.00 / 1.00 / 1.00 / 0.77 / 0.31）；
- **实测结果**：与预期完全一致（见 `LiYaxuan_C4A_评审报告.md`）；
- **回归验证**：修复了 3 个 bug（C4 过滤时机、评分公式解析、可执行内容误匹配），每次修复后重跑全量语料。

## 九、创新点

1. **check item 谓词化**：把 rubric 里的英文 check item 翻译成可计算谓词，评分过程完全可审计；
2. **可执行内容专项检测**：.skill/.py 真实可执行文件优先于文件名关键词，避免"说明文档被当成可执行内容"的误判；
3. **README 类文件过滤**：目录说明文件不会污染作者识别；
4. **LLM 降级设计**：国产大模型 API 缺席时规则引擎完整可用（评审能力零云端依赖）。
